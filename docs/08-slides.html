Bloco 1 · Contexto da solução

O problema e o que o case exige

Problema de negócio

  • Liberar crédito rotativo automaticamente para clientes com perfil aprovado
  • Regras complexas: histórico de crédito, perfil de gastos e comportamento recente
  • Simular a avaliação para uma lista de clientes (RF1–RF3)
  • Relatório de aprovados, reprovados e valores (RF5)
  • Adicionar regras sem refatorar o motor (RF4)
  • Documentar e justificar os critérios de decisão (RF6)

NFRs (7)

  • Latência — decisão em até 1 segundo
  • Escalabilidade — picos de 10.000 avaliações/min
  • Precisão — sem liberação indevida / bloqueio indevido
  • Extensibilidade — regras sem refatoração complexa
  • Segurança/LGPD — PII protegido, acesso controlado
  • Observabilidade — métricas, logs e alertas
  • Resiliência — continuidade em falhas temporárias
1 min: O case não pede integração real com sistemas bancários — mocks são aceitos, mas as decisões precisam ser justificadas. Vale destacar que os 7 NFRs viraram a seção 4.1 de docs/04 e cada um tem item no backlog (docs/06).
Bloco 1 · Contexto da solução

Arquitetura — Ports & Adapters em 4 camadas

API / Adapter (FastAPI)→ Caso de Uso (orquestrador)→ Cadeia de Regras (CoR)→ Persistência (SQLite / memória)

Fluxo de uma avaliação

1 · Validação do payload — fail-fast no domínio ↓ 2 · Bloqueio: R1 score → R2 atrasos (corta a cadeia) ↓ 3 · Scoring: R3 → R4 → R5 (acumula até 30 pts) ↓ 4 · Decisão: sem bloqueio e peso ≥ 20 (2 de 3) ↓ 5 · Cálculo do valor máximo + ajuste ↓ 6 · Persistência, relatório e métricas

Estado persistido de cada avaliação: RECEBIDO → EM_AVALIACAO → AVALIADO/FALHA

Domínio puro

  • app/domain sem framework — testável sem HTTP/banco
  • dataclasses frozen + validação fail-fast
  • Regras como funções puras

API — 6 endpoints

  • POST/avaliacoes — avalia um cliente
  • POST/avaliacoes/batch — avalia a lista (RF1)
  • GET/relatorio — JSON; Accept: text/csv → CSV
  • GET/metricas — volume, latências, alertas
  • GET/saude — healthcheck
  • GET/docs — Swagger / OpenAPI
2 min: Dependências apontam para dentro: api → application → domain ← infrastructure. O diagrama de componentes completo está em docs/02 (Mermaid). A máquina de estados persistida e a chave de idempotência são os pontos de extensão que preparam a migração para SAGA sem refatoração.
Bloco 1 · Contexto da solução

Padrão central: Chain of Responsibility

R1 score ≥ 600→ R2 atrasos ≤ 2→ R3 uso do limite (10)→ R4 estabilidade (10)→ R5 perfil de gastos (10)→ decisão + valor

Valor máximo = min(fatura × 1,0; limite_total × 50%; R$ 10.000) × ajuste 0,50 + 0,50 × peso/30

Design — onde as regras são encadeadas

# credito-rotativo/app/domain/rules/__init__.py
REGISTRY = {"score_minimo": ScoreMinimoRule, ...}
ORDEM_PADRAO = ["score_minimo", ..., "perfil_gastos"]

def montar_cadeia(config):
    atual = REGISTRY[ORDEM_PADRAO[0]](**config.params(...))
    for nome in ORDEM_PADRAO[1:]:   # encadeia em ordem
        atual = atual.set_next(
            REGISTRY[nome](**config.params(nome)))
    return atual
  • rules/base.py — AbstractRule encadeia e faz o short-circuit; a regra implementa só avaliar()
  • Bloqueio (R1, R2) corta · scoring (R3–R5) acumula → decisão: sem bloqueio e peso ≥ 20 (máx 30 → 2 de 3)

Nova regra em 3 passos (Open/Closed)

  • 1. Crie app/domain/rules/minha_regra.py — implementa só avaliar(context)
  • 2. Registre em REGISTRY e ORDEM_PADRAO (no mesmo __init__.py)
  • 3. Thresholds da regra viram env var — sem tocar no motor, na API nem nos testes

Ajuste sem deploy — env vars CREDITO_*

  • CREDITO_SCORE_MINIMO = 600 → R1
  • CREDITO_MAX_ATRASOS_MESES = 2 → R2
  • CREDITO_UTIL_LIMITE_MIN/MAX = 0,10 / 0,90 → R3 (peso 10)
  • CREDITO_ESTABILIDADE_MAX = 0,30 → R4 (peso 10)
  • CREDITO_PERFIL_GASTOS_FATOR = 1,5 → R5 (peso 10)
  • CREDITO_LIMITE_APROVACAO = 20 → decisão (2 de 3)

pydantic-settings: tipadas, com default e validadas no boot (fail fast)

2 min: o código ao vivo é o app/domain/rules/__init__.py — mostrar montar_cadeia e depois um arquivo de regra só para provar que implementa só avaliar(). Pergunta de retomada para a demo: “regras_aplicadas mostra onde a cadeia parou”. O card de env vars responde o NFR de extensibilidade: mudar threshold é trocar a env, sem redeploy; em produção, o 20/30 viraria curva calibrada com dados reais.

Bloco 2 · Decisões técnicas e trade-offs

Decisão → alternativa → por quê → quando reavaliar

Python + FastAPI

  • Alternativa: Java/Kotlin (stack do Itaú)
  • Por quê: clareza e velocidade no prazo de 7 dias — sobrou tempo para testes, docs e NFRs
  • Reavaliar: se virar produto de time Java

Chain of Responsibility

  • Alternativa: Strategy
  • Por quê: fluxo sequencial e fixo (bloqueio → scoring → decisão)
  • Reavaliar: fórmulas de valor por produto (método de cálculo já isolado)

CoR + orquestrador

  • Alternativa: SAGA (Temporal)
  • Por quê: avaliação é read-only — sem efeitos colaterais a compensar
  • Reavaliar: reserva de limite + contrato + notificação

Short-circuit

  • Alternativa: avaliar todas as regras
  • Por quê: reprovar imediatamente economiza processamento
  • Reavaliar: precisar laudo completo (hoje: motivos até o corte + regras_aplicadas)

Env vars (12-factor)

  • Alternativa: YAML / config em código
  • Por quê: trocar threshold por ambiente sem redeploy; validação no boot (fail fast)
  • Reavaliar: config centralizada em muitos serviços

SQLite

  • Alternativa: Postgres
  • Por quê: primeira versão single-node; persistência real sem infra extra (repositório atrás de interface)
  • Reavaliar: múltiplos nós / escrita concorrente
7 min: cada decisão em 4 tempos, e o “quando reavaliar” é o ponto forte da discussão — são decisões reversíveis por design (interface de repositório, método de cálculo isolado, config por env var). Em produção, o orquestrador vira step de um SAGA orquestrado e a máquina de estados (RECEBIDO → EM_AVALIACAO → AVALIADO/FALHA) + chave de idempotência já sustentam a retomada. 2PC/XA é evitado em escala por fragilidade.

Bloco 3 · Qualidade, operação e evolução

Observabilidade, segurança/LGPD e resiliência

Observabilidade

  • /metricas: volume, taxas, p50/p95, replays e alertas
  • Logs JSON por linha: eventos, correlation_id, sem PII
  • Alertas: p95 > SLO (1 s), taxa de erro > 5%, reprovação ≥ 90% — calibráveis em CREDITO_ALERTA_*
  • Transição vira log (sem repetição a cada poll)

Segurança / LGPD

  • CPF → SHA-256 + salt no adapter; domínio nunca vê o CPF
  • Nenhuma PII em log, relatório ou métricas (só cpf_hash)
  • Auth/autorização no API gateway — app é serviço interno (decisão registrada)
  • Container sem privilégio + healthcheck

Resiliência

  • Idempotência: X-Idempotency-Key (padrão: hash do CPF) → retry não reavalia; vira replays na métrica
  • Retry + backoff no write do SQLite só para erros transitórios (CREDITO_PERSISTENCIA_RETRY_*)
  • Estado FALHA → EM_AVALIACAO retomável; volume = dados sobrevivem a reinício
3 min: Sobre autenticação — pergunta provável do Q&A: o case pede “controle de acesso restrito, autenticação, autorização”; a decisão foi deixar no gateway, antes do tráfego chegar na aplicação (justificada em docs/06, Epic 7). Métricas são em memória — em produção: Prometheus/Grafana.
Bloco 3 · Qualidade, operação e evolução

Evolução — o que muda e o que não precisa mudar

Próximos passos

  • Workflow engine (Temporal) no lugar do orquestrador — sem tocar nas regras
  • Fila + workers para picos (o batch já é endpoint)
  • Postgres + réplicas — interface de repositório isola a troca
  • Prometheus/Grafana e RBAC real no gateway
  • Strategy para fórmulas de valor por produto; regras com ML

O que já existe — e o que cada peça destrava

  • Orquestrador = 1 caso de uso (app/application/avaliar_credito.py): a ordem valida → cadeia → calcula → persiste está toda nele — no futuro, trocar por um workflow engine (Temporal) é substituir só esse módulo, API e regras ficam como estão
  • O estado da avaliação já é salvo com ela (RECEBIDO → EM_AVALIACAO → AVALIADO/FALHA) — é esse registro que um retry ou fila lê para retomar de onde parou; já está modelado e persistido hoje
  • Regras são funções puras (entra o perfil, sai o resultado, sem HTTP/banco) — uma delas pode virar serviço remoto trocando só a implementação: assinatura igual, a cadeia continua chamando do mesmo jeito
  • REGISTRY + interface de repositório — regra nova entra com 1 linha no registro; banco novo = implementar a interface + env var (mesmo caso de uso)
1 min: A mensagem: cada evolução da lista da esquerda troca um ponto só — o módulo do orquestrador, a implementação interna de uma regra, a implementação do repositório — sem refatorar motor, API nem testes de domínio (princípio: pagar complexidade só quando o problema aparecer).
Bloco 4 · Estratégia ampliada

Como priorizei — e o que ficou de fora

Ordem de decisão

  • Requisitos → modelo de domínio e invariantes (fail-fast) — base de tudo
  • Padrão da cadeia + escopo (CoR vs SAGA) — evita over-engineering
  • Regras parametrizáveis (env vars) — mudar regra sem deploy
  • Orquestrador + cálculo + relatório (fecha RF2–RF5)
  • NFRs: idempotência, métricas, LGPD, Docker
  • Testes + Swagger + documentação

Cada etapa entregou valor testável; a máquina de estados e os pontos de extensão para SAGA vieram depois, quando já existia fluxo a proteger.

Fora de escopo — e por quê

  • Auth na aplicação — fica no API gateway, antes do tráfego chegar
  • Fila/workers reais — batch em memória já atende 10k/min medido
  • Eventos de domínio publicados — ponto de extensão no orquestrador, sem broker
  • Integrações bancárias — fora do escopo do case (mocks aceitos)

Limitações conhecidas

  • Single-node · métricas em memória · auth delegada ao gateway
2 min + 1 min encerramento: Priorização = resolver primeiro o que destrava as outras decisões (domínio e padrão), depois extensibilidade, depois NFRs, depois superfície de apresentação (testes/docs). Próximo passo: productionizar observabilidade e transportar a cadeia para a fila.
